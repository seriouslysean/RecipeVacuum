# Client notes

What WoW Forever's client does, where the addon depends on it. Measured in game on build 1.60.1.71037 unless a file is named. Blizzard's UI source for this client: [Gethe/wow-ui-source, `forever` branch](https://github.com/Gethe/wow-ui-source/tree/forever).


Log lines are logfmt since 2026-11-27, written by the kit from `toolkit:Trace(ns.module, "event", "key", value, ...)` (kit `docs/standards.md`, "Working build"; kit decision 0067). Measurements quoted below from earlier sessions keep the older prose form, as the logs of those dates hold them: `UI panel shown with …` is now `list shown id=… rows=… groups=… ms=… frames=…`, `UNLEARNED profession N: … known recipes marked met` is `known id=N found=… new=… no_trainer=…`, `TRAINER scan of N services …` is `trainer scan services=N steps=… ms=…`, `TRAINER learned pass …` is `trainer pass n=… npc=… used=…`, `SEEN …` lines are `window …`, `recipe seen …` and `shown profession …`, and the LAYOUT lines come only from the Window Layout [Record] row.

## Gamepad

With the Gamepad UI (Steam Deck), Blizzard's own code refuses to run on anything an addon wrote, so Recipe Vacuum writes nothing into Blizzard's frames, lists, menus or panels and opens none of its windows (owner decision; the same rule for every input method, not a gamepad mode). Measured in game on WoW Forever:

- `SmartNavigation.lua` `EnsureIsSecure` stops when it reads anything addon code wrote. After rows were inserted into the profession recipe list, the d-pad stopped moving (stack: `Navigate`, `SelectButton`, `EnsureIsSecure`).
- `ADDON_ACTION_FORBIDDEN` named Recipe Vacuum for `SetPreferredGamepadInteractTarget`.
- Opening the character window from the gamepad radial failed with "attempt to compare a secret number value (execution tainted by 'RecipeVacuum')".
- `MenuUtil.CreateContextMenu` and `Menu.ModifyMenu` entries from addon code taint. So does opening the world map from addon code under the Gamepad UI, and moving an open map to another zone; a `/run` line in a secure macro too (kit decision 0068, Deck, 2026-11-27). Map Pin opens it out of combat through a secure button laid over our control, whose macro is the game's own `/mappin <map> <x> <y>`: Blizzard's handler sets the waypoint and opens the map on its zone (`WaypointLocationDataProvider.lua:213-229`), clean on the Deck (build 75df552). The press then reaches our control, which super-tracks the pin and says so. Protected frames cannot be hidden or moved in combat, so the secure buttons are hidden and unanchored on `PLAYER_REGEN_DISABLED` and placed again on `PLAYER_REGEN_ENABLED`; in combat Map Pin sets the pin and says so without the map (owner, 2026-11-27: "I think just adding the pin and logging the message is probably fine"). The map takes the left panel slot and pushes the profession window to the center, which ran our panel off the screen; the panel now steps aside whenever the profession window is not in the left slot, as it does when Looking For Group takes the center (kit decision 0077).
- `C_Map.GetBestMapForUnit("player")` can give a continent: Odd Child was saved on map 1415 (Eastern Kingdoms), 1 of 83 saved positions, cause unknown. `ns.ZonePosition` moves such a position to the zone under it on save and on read (kit decision 0078).

What is no longer done: unlearned rows in the recipe list, source marks on rows, the source line, item row and map button in the recipe pane, the Recipe Vacuum section of the filter menu, the first-run help tip, and any call that refreshes Blizzard's list. Unlearned recipes will live in Recipe Vacuum's own panel beside the window, fed by `ns.GetUnlearnedRecipes`.

## Panel

`Panel.lua` draws Recipe Vacuum's own list of what a character has found and not yet learned, beside the Professions window. The prototype was seen on the Steam Deck (owner, 2026-11-26): the d-pad reaches the panel, scrolls to the bottom, nothing is blocked. Everything below is as built; what is replaced is named only where a reader would put it back.

### Placement and frame

- The panel is a child of `ProfessionsFrame`, so it shows and hides with the window and the Gamepad UI treats it as part of it. It anchors to `ProfessionsOverviewTab`'s top right, 60 px up to the window's top (Camelot `Blizzard_ProfessionsFrame.xml`; all tabs share one x), and takes the window's height whenever it shows. About 230 px are free right of the tab column at 1280x800 before the quest tracker; the panel is 280 wide (`PANEL_WIDTH`) and may overlap the tracker a little.
- It is a `PortraitFrameTemplate` (`Blizzard_SharedXML/Mainline/SharedUIPanelTemplates.xml:658`), as the window is (`Blizzard_ProfessionsFrameBase.xml:5`; owner, Deck, 2026-11-26: "a similar outline to the blizzard window, the alt color/texture headings and an icon on the top left"). The template's own API sets it up: `SetTitle` with the name and the version in a dim color escape (one string; "dev" in a working build, the copy's short commit and second in a Deck copy), `SetTitleOffsets(nil, -5)` because the close button is hidden (the panel follows the window), and `SetPortraitToAsset` with the TOC's `IconTexture`, so the icon changes in one place.
- Art is the window's own under Camelot, which hides the list's inset border (`Camelot/Blizzard_ProfessionsFrame.lua:136-141`) and the schematic form's inset frame (`Camelot/Blizzard_ProfessionsCrafting.lua:18`). The frame's `Bg` is `Profession-Background-Overview` with its top streaks hidden. The dark page and title band are the left share of `Profession-Background-Template2` (665 x 570, drawn at 3, -21, `Blizzard_ProfessionsFrame.xml:71`; the atlas has no pane borders, checked on the decoded atlas file from wago.tools, build 1.60.1.71139). The list area is only the `Professions-background-summarylist` atlas, no border.
- The list area sits 5 px in from the frame's left, right and bottom, as the window's list sits 5 px from its frame (`Blizzard_ProfessionsCrafting.xml:138-139`). The recipe column is 304, the width Forever gives the window's own (`Camelot/Blizzard_ProfessionsCrafting.lua:25`, `RecipeList:SetWidth(304)`): 276 for the list, 8 left inset and 20 scroll bar column (the window's `ScrollBox` runs from x 8 to right -20, `Blizzard_ProfessionsRecipeList.xml:76-79`), plus 2 x 5 (owner, 2026-11-27: "Match 304"; it was 242 for the list before). The panel is 34 px wider than before, so on the Deck's 1280x800 it covers about 34 px more of the quest tracker beside it.
- The portrait corner stands 13 px outside the frame (`NineSliceLayouts.lua:20`) and the tabs begin 60 px below the window's top, so the panel keeps 2 + 13 from the tab column and no corner covers a tab. The corner atlas size is not in the source, so the vertical overlap was not measured.
- Content starts 40 px below the frame's top (`CONTENT_TOP`): the window's own `RankBar` is at y -40 (`Blizzard_ProfessionsCrafting.xml:199`), and the top edge art is taller than the 21 px at which the background starts (`SharedUIPanelTemplates.xml:629`), which clipped a line placed higher (owner, Deck, 2026-11-26). The discovery bar sits there; the list area starts at the top of the crafting page's own `RecipeList`, read when shown (72 px below the window's top, `Blizzard_ProfessionsCrafting.xml:157`; owner, 2026-11-26: "Our header should match the height of the official layout"). There is no separate count line.
- The list's background is drawn at the full height of the page's list and clipped at the list's end, so the list reads as a closed box over the page, as the window's list does, and the gap the details' ring hangs into shows the page (owner, Deck, 2026-11-27, on the background run into the gap: "The circled gap bar is really weird"). It was squeezed into the shorter list before, and its dark bottom fade then showed as a bar above the box.
- Other windows: a post-hook on `UpdateUIPanelPositions` reads `GetUIPanel("center")`, and the panel hides while another window holds it. Unverified on the Deck: whether Professions itself ever sits in the center slot (the code ignores that case).
- The rank mark (`Ranks.lua`) augments Blizzard's rank bar rather than replacing it. It is our Button under `UIParent` (strata HIGH, so it draws over the window), shown and hidden with the crafting page through hooks on its `OnShow` and `OnHide`, and anchored to the window's link button or rank bar only to read their position, so nothing is written into a Blizzard frame. It is not a child of the page (the Gamepad rule) nor of our panel (which hides when it has nothing to list). It is how a player finds the next rank's trainer, so it must stay reachable by d-pad (owner, 2026-11-26: "Otherwise they get locked out"): it is never marked ignored for navigation, the d-pad reaches it as the nearest button between the window and the panel (seen on the Deck, 2026-11-26), and it has no jump override.

### List

- Which recipes: the show rule and rank bands in `docs/data.md` ("Show rule", "Required skill"). The skill line is the page's `professionInfo.professionID`. Unverified in game: that this is the open expansion's child line on Forever, and that `skillLevel` and `maxSkillLevel` on the page's `professionInfo` are the character's skill and the rank's cap.
- Order is ascending required skill, then name; a recipe with no known requirement uses its `maxTrivialLevel`, the nearest threshold `TradeSkillRecipeInfo` (`TradeSkillUITypesDocumentation.lua`) gives (`ns.SkillOf`). The client has no field for the skill a recipe is learned at.
- The list is a plain `ScrollFrameTemplate` with Blizzard's `MinimalScrollBar`, the recipe list's bar, its thumb sized to the share in view and hidden while the list fits; one own Button per row and heading, because SmartNavigation only calls `SetVerticalScroll` on a plain scroll frame. The bar's 20 px column is reserved only while the bar shows, so rows use the full width when the list fits.
- Rows are `ProfessionsRecipeListRecipeTemplate` Buttons (`Blizzard_ProfessionsRecipeList.xml:134`), made with `CreateFrame` and filled directly (the template needs no ScrollBox or data until `Init`, which is not called). They are 20 high with 1 px between (`Blizzard_ProfessionsRecipeList.lua:16-20`), indented 10 under their heading, 5 px list padding, `GameFontHighlight_NoShadow`, the template's hover (`Professions_Recipe_Hover`) and selected looks, no icon. The template's `OnEnter` and `OnLeave` are replaced by ours (theirs read a ScrollBox element).
- Blizzard's skill-up slot (26 x 15, 9 px left of the row) holds the arrow or stays empty, as in its list, and the name starts 4 px after it. A row shows no skill number (owner, Deck, 2026-11-27: match the vanilla presentation); the required skill is in the details. Marks (source types) stack from the right edge.
- The name is white when the character's skill can learn it now, and grey (`DISABLED_FONT_COLOR`) when the required skill is higher or the recipe is `disabled` or locked by a specialization; it turns white under the cursor.
- A row shows Blizzard's own skill-up arrow (`Professions-Icon-Skill-High`, `-Medium`, `-Low` for Optimal, Medium, Easy; `Blizzard_ProfessionsRecipeList.lua`, `SetRecipeInfo`) when the recipe's `canSkillUp` is true and the name is not dim; Trivial shows none. For unlearned recipes the client's `relativeDifficulty` and `canSkillUp` are real (Deck, Corvus, 2026-11-27: Alchemy at 206 gave 0 x29, 1 x3, 2 x2, 3 x9 and `canSkillUp` true; at a rank cap, First Aid and Cooking 150/150, `canSkillUp` was false for every recipe; docs/data.md, "Skill-up arrows"). Working-build trace "skillups id=N can=… above=…" (one line per build) names the branch that decided: "none: above skill 40 > 20", "none: cap 75/75", "none: client canSkillUp false at 20/75", "none: Trivial at skill 20", "arrow Optimal".
- A bracketed count after the name shows how many the bags and bank could make (`Blizzard_ProfessionsRecipeList.lua:228`, `SetCraftableCount`). The client counts only learned recipes, so an unlearned one is counted from its basic reagents, read once per recipe; a schematic that is not loaded yet counts 0 and is asked again on the next redraw. `BAG_UPDATE_DELAYED` refreshes the counts; a bank slot change only clears the held counts, the next redraw reads them.
- Headings are `ProfessionsRecipeListCategoryTemplate` Buttons (`Blizzard_ProfessionsTemplates/Blizzard_ProfessionsRecipeList.xml:122`, a `ListHeaderVisualTemplate` from `Blizzard_SharedXML/ListTemplates.xml:22`): 25 high, `Game15Font_Shadow` title in `NORMAL_FONT_COLOR`, the plus or minus `CollapseButton` at the right, the template's progress bar hidden. One heading per rank band that has recipes (bands of 75 by required skill). The text is the rank spell's subtext ("Journeyman", `C_Spell.GetSpellSubtext`, `ns.BandTitle`, `docs/data.md`, "Rank spells"; the spell's name is only the profession's), or "Skill 76 to 150" when no rank spell is known. Rank spells the character has not learned are not loaded until asked for, so the heading draws again when the spell's data arrives.
- While collapsed a heading shows the found count as a smaller dim "[n]" (`GameFontDisableSmall`, a second font string after the title's width). A click, or A on the gamepad, toggles a band with our own `OnClick` (the list's would toggle a ScrollBox node); open or closed is kept for the session only. No menu or dropdown, which taint (Gamepad).
- Every band starts open, as Blizzard's categories do, and one the player closes stays closed for the session (`Blizzard_ProfessionsTemplates.lua`, `collapses`; owner, 2026-11-26: "We need to match blizzard"). That replaced starting the bands above the character's skill collapsed.
- Spacing follows Blizzard's tree: a category holds a 1 px `topPadding` element above its recipes and a 10 px `bottomPadding` one below (`Blizzard_Professions.lua:960-974`; extents `Blizzard_ProfessionsRecipeList.lua:127-133`), each followed by the view's 1 px spacing, so an open category ends 12 px after its last row. Headings are 20 + 5 (`:108-132`). A collapsed band has no children, so none of that.
- Hidden when empty (owner, 2026-11-26): the panel hides when the list it would show is empty before any search or filter (nothing found, or everything found learned) and no search or filter is on (the search box text, `GetOnlyShowSkillUpRecipes`, `GetOnlyShowFirstCraftRecipes`). While one is on, the panel stays when nothing matches and shows the game's own `CUSTOMER_CRAFTING_ORDERS_BROWSE_NO_RESULTS` ("No recipes found", `GlobalStrings`, build 1.60.1.71139). The update decides before the panel shows, so opening never flashes it. It runs while the panel is hidden for being empty too: a search change, the page's `Init`, the list and learning events and `ns.SourcesChanged` (a find) each ask for one, and the first that finds something shows the panel again. The rank mark is on the crafting page, so it stays. Unverified in game: the list events fire while the panel is hidden.
- Filters, read from `C_TradeSkillUI` as `Blizzard_Professions.lua` reads them (`GetCurrentFilterSet`): the search box text (folded with `CaseAccentInsensitiveParse`; `HookScript` on the recipe list's `SearchBox` `OnTextChanged`), `GetOnlyShowSkillUpRecipes` (hides recipes whose `relativeDifficulty` is trivial), `GetOnlyShowFirstCraftRecipes` (`firstCraft`). Not followed: "Have materials" (nothing unlearned is makeable) and "Show unlearned", which Forever turns off by default and which emptied the panel on the Deck (2026-11-26). Not applied: inventory slot, category and source filters, which have getters for the filter state but none that places a recipe in a slot or category.
- The unlearned recipes are read in slices of 2 ms a frame (`ns.GetUnlearnedRecipes`, a coroutine per profession; the cold read took 26.5 ms in one frame on the Deck, the panel update 44.5 ms) and kept in two stages per profession. Stage one is the client's answer (the unlearned candidates and the categories its learned recipes establish); a recipe learned clears it, and a rank or cap change found by comparing `GetProfessionInfo` before and after (`SKILL_LINES_CHANGED` fires for every skill line, three times at each login) only reads each candidate's difficulty again. Stage two is ours (source summaries, categories, the list) and a found source clears only it, so a find costs no client read; the cold read was 26.5 ms. `ns.LinkPending` yields after each item, and one item's tooltip is the indivisible part, logged as "item linked id=N ms=X" from 1 ms. The finish trace names each stage's ms and the stage of the worst slice. The panel holds back while the read runs and draws when it ends (`ns.RequestUpdate`). Window opens and `TRADE_SKILL_DATA_SOURCE_CHANGED` no longer clear it. Working-build timings: "unlearned slice", "panel update list", "layout", "details" and the trace "recipes read id=N slices=S".
- Refresh events: the page's `Init` (a filter change makes the client send `TRADE_SKILL_LIST_UPDATE`, which rebuilds the page), `TRADE_SKILL_LIST_UPDATE`, `TRADE_SKILL_DATA_SOURCE_CHANGED`, `NEW_RECIPE_LEARNED`, `SKILL_LINES_CHANGED`, `BAG_UPDATE_DELAYED`. Every trigger only asks for a rebuild on the next frame, so one build runs however many asks.
- Rebuild rule: the panel lays out its items and a signature of them (profession, search text, each band with its open state and count, the recipe IDs of open bands in order). An equal signature changes nothing on screen but the text, colors and marks of the rows already there, refreshed in place, so a skill rise, a refreshed cache or the window's repeated list events never move a row under the gamepad cursor. The Deck log showed 22 rows rebuilt every 2 to 30 seconds with no input before this.
- Build cost: the prototype's first Deck run froze the profession window for about 6 s, with 518 rows (every unlearned Blacksmithing recipe in the client, later expansions included) built three times in one second. Now the list is filtered before any row exists, rows are made in steps of at most 4 ms and 40 rows (`BUILD_BUDGET_MS`, `ROWS_PER_STEP`), frames are made ahead ("Frame pool" below) and kept across professions, and the list stays transparent only until every item in the view and one view below it is placed (`Reveal`, trace line "list visible rows=N ms=X"); the rest is built behind it in the same budgeted steps, with the child's full height set up front so the scroll bar is right, and the navigation jumps are set again at the reveal and at the end (rows past the built ones appear as they are built if the player scrolls ahead). A build with enough frames is one fill pass, so it is visible at once. Before this the list waited for the whole build, about 4.5 s on the Deck's first window of a session while rows were created. When the client's names or factions are still loading, the first show waits up to 1 s (`WAIT_SECONDS`) instead of showing and redrawing; one retry follows after that. The trace line "list shown" and the `panel build` timing are the build steps' time only; the list read, the details, the reveal and the navigation jumps are outside it (`panel update` and the worst-frame figures name them). Unmeasured: the per-profession cost of one fill pass. Deck runs (build 1126.1644): 133 rows in 1023.7 ms over 136 frames, then 151 rows under 4 bands in 1208.1 ms over 154 frames, of which row creation was 1128.7 ms (about 7.5 ms per `ProfessionsRecipeListRecipeTemplate` row, one row a frame under the 4 ms budget) and everything else under 50 ms; the fixed pool of 60 was too small for a 151-row list. The cause found by reading the code, not yet measured: a row's label width was read back with `GetLeft` right after the row was anchored, which forces a layout pass over every anchored row, so a build grew with the square of the list. The width is now computed from the row's known width, the marks' sizes (`ns.MarkWidth`) and cached text widths, a row writes only what changed, and the in-place refresh (bags, counts, colors) runs in budgeted steps. Frame spikes (Deck, build 1126.1713, one session): "UI panel shown with 58 rows ... built in 24.6 ms over 1 frames" (count 9.1, lock 8.5, show 1.9, marks 1.1) and 60 rows in 23.6 ms over 1 frame, against 7.8 to 8.0 ms for the same 60 rows warm; the game's own peak for the session was 54.46 ms, 74 frames over 5 ms and 39 over 10 ms, where earlier sessions peaked at 1.5 to 4.2 ms. The budget held only while frames were being made: the loop's test was "nothing made yet, or under the budget", so with a full pool every row passed it and a whole list was one frame, a cold row costing 0.1 to 0.2 ms (the recipe's schematic for its reagents, the item's tooltip for its lock) and a warm one under 0.07 ms. Now the budget ends a frame whatever the work, one item at least advancing, so a cold 60-row list is about 6 frames of 4 ms plus one row, and the reveal shows once the view is placed. A reagent's held count is read once until `BAG_UPDATE_DELAYED` or a bank slot change (`craftable.held`), and the build's end line gives the frames used, the worst frame and the most items in one frame. The 54 ms is not named by the log: the saved timing table shows `trainer scan` at 16.5 to 21.3 ms average and 24 to 30 ms slowest (a tooltip per service, read in one frame by the old scan with the trainer's filters on; it now runs in 3 ms steps under the player's own filters, "Trainers" below, and repeat reads of a trainer skip the tooltips) and `unlearned recipes` at 31.2 ms slowest (the cold read of a profession's recipes, once per profession until a find changes), which together are about 55 ms if a trainer visit lands both in one frame. That is a reading of the numbers, not a measurement; the working build now times `heard <event>` for every event of `Heard.lua`, `panel update` (the whole redraw) and `pool slice`, so the next Deck session's PERF lines name it. A working build's trace line "build parts" splits a build into create, place, selected, lock, name, count, skill, marks, width and show, with the longest frame; read it before changing a row again.
- Tooltips: a row shows the game's own tooltip for the item the recipe makes (`GetRecipeSchematic`, `outputItemID`, `GameTooltip:SetItemByID`), or the recipe's spell when it makes none, so other addons' tooltip hooks add their lines; our source lines follow. The panel sits at the screen's right edge, where `ANCHOR_RIGHT` clamps a tooltip back over it, so `ns.OwnTooltip` hangs the tooltip off the panel's left edge, level with the owner, when less than a tooltip's width is free on the right (the Map Pin list's entries included; the rank mark sits over the window, so it keeps `ANCHOR_RIGHT`).

### Discovery bar

- The bar is the skill bar's own art, 18 px high like the window's `RankBar` (`Blizzard_ProfessionsCrafting.xml:197-199`, owner's pick, `bd7a5fe`), centered on the panel under the title as the window centers its skill bar and as wide as clears the portrait ring (158 px; owner, 2026-11-26), on the line the window's rank bar sits on. It is a plain frame with a mouse tooltip, so the gamepad cursor does not land on it, with the panel's own `Number12FontOutline` text.
- The art is `Professions-skillbar-bg` and `Professions-skillbar-frame`, placed as `Blizzard_ProfessionsRankBar.xml` places them and cut into two 16 px ends and a stretched middle by the atlas's own texture coordinates, because the engine's slice margins clipped the ends (the art has 3 px clipped corners; `a61d2cb`).
- The fill is the reputation bar's Friendly green (`UI-HUD-ExperienceBar-Fill-Reputation-Faction-Green`, `ReputationBar.lua`; owner's pick, `40d2baa`), under the skill bar's own mask (`Professions-skillbar-mask`) set as `Blizzard_ProfessionsRankBar.xml` sets it, 5 in, 3 down and 12 narrower than the bar; the mask's width is the share shown. It is not the profession rank bar's fill, whose fills are each profession's own animated art recolored by its code, and not the rank bar template itself, whose 453 px of art distorted at this width (owner, 2026-11-26).
- Per source level (`docs/data.md`, "Discovery"; owner, 2026-11-26: the total is a spoiler below public data): at Public "%d / %d discovered" with the fill at the share found; at Self Found and Friends "%d discovered" over the empty frame (no fill, because the fill's width encodes the total) and a tooltip that words only the count. `ns.GetListedRecipes` gives found (the list ignoring search and filters) and total (every candidate of the skill line). The bar changes when the setting does (`ns.SourcesChanged` asks the panel to update) and ignores the window's skill events.

- A shown list never blanks for its own profession (owner's Deck video, 2026-11-27 12:57: "every time a craft finishes our list of items rerenders and disappears", about 0.25 s). A craft's skill rise fires `SKILL_LINES_CHANGED`; a rank or cap change clears the unlearned summaries (`Unlearned.lua`, `ForgetSummaries("a rank or cap change")`), so the next `GetListedRecipes` is a fresh sliced read and returns nil for a frame. The panel answered nil by hiding the list and forgetting its signature, so the read's end rebuilt every row from nothing behind a hidden list until `Reveal`. Now nil for the profession already shown keeps the list up ("list kept id=N reason=reread"), and the read's end, with the same content, refreshes in place. A real content change of a shown list (a search, a new find) relabels its rows while the list stays up ("list build id=P rows=N shown=kept"); only a new profession is hidden until its view is placed.

### Frame pool

Creating a row is the whole build cost, so the frames are made before the window opens (owner, Deck, 2026-11-26). The pool is in `Panel.lua` (`pool`, a table because the file is at the client's limit of local variables).

- Start: 5 s after `PLAYER_LOGIN` (`pool.startDelay`), so it never competes with the login's own work; in combat it waits for `PLAYER_REGEN_ENABLED`. The templates live in `Blizzard_ProfessionsTemplates`, which the game loads with the professions window; the pool waits for that load (`EventUtil.ContinueOnAddOnLoaded`) and never loads it itself, since loading a Blizzard addon from addon code runs its files tainted (kit `docs/client-notes.md`). So the session's first window open builds the rows it needs as before, and the pool fills the rest in the background for every later open.
- Target: the most rows, and the most rank bands, any of the character's professions would list now, counted from the saved finds without the window: every recipe in the layers the chosen level reads (found, shared, included) or met within the level, whose skill line (`GetTradeSkillLineForRecipe` through `ns.ProfessionLine`) is one of `GetProfessions`, per profession; a band is `ns.BandOf` of the seed's required skill, else its trivial point, else the first band. Learned recipes are not taken out, so it is an upper bound. Margins: 10 rows and 1 heading (`pool.rowMargin`, `pool.headingMargin`). It never shrinks, and is counted again, in the same budgeted slices, whenever finds change (`ns.RequestPanel`, from `ns.SourcesChanged`). Frames are never removed.
- Slices: at most `BUILD_BUDGET_MS` (4 ms) and `ROWS_PER_STEP` frames per frame, headings first. The 7.5 ms a row once cost came from a layout pass that is gone (`POOL rows made 20/85 ... 25 this frame in 4.1 ms`, about 0.16 ms a row), so the 4 ms budget alone ends a slice, and one item is always done. The budget runs from the start of the frame, so `Update`'s list read, layout, details and first build step share it (`frameStart`). A cold row still reads the schematic and tooltip in its own `ShowRow`: unmeasured since the rule was removed, read `UI build parts` on the next Deck session. The details' frames (eight reagent rows and the two Map Pin buttons) are made ahead first, on the holder, and adopted by the details; the first details draw of a session, when the pool has not run yet, made them in its own frame (21.57 ms slowest, 27.73 ms for the whole update on the Deck, build a07985b), so the working build now times `details data`, `details header`, `details reagents` and `details map`. A slice in combat stops; the end of combat resumes it. A list build in progress makes frames itself and the pool waits.
- Frames made before the panel exists are children of a hidden frame and move into the list's scroll child when a build uses them (`SetParent` on our own frame).
- A window that opens before the pool is ready builds the rest as before.
- Waits while the window works (Deck log, 2026-11-27 11:14): the session's first window was Jig's linked Leatherworking (810 recipes counted). The pool, which starts with that window, then made exactly one frame a slice at 6.6 to 11.5 ms each, details' frames, headings and rows alike, 98 slices in 715.6 ms, where at 10:10 the same pool made 18 to 22 rows a slice in about 4 ms (0.2 ms a row). Blizzard's row and heading templates do nothing on load that depends on the window's state (`Blizzard_ProfessionsRecipeList.lua:190-196`, `:239-247`), and the game's own profiler charged Recipe Vacuum only 3 frames over 5 ms that session, so the cost sat outside our code: most likely Lua garbage collection after the window's own allocations (322 ms to open, 17 walk steps), unverified. ### Gamepad navigation

SmartNavigation honours an override from addon code only out of combat, and `SecureHelper` refuses to set one in combat (`SmartNavigation.lua:1503-1520`). Overrides come from `SmartNavigation_AddJumpNavigationOverride` and `SmartNavigation_ClearJumpNavigationOverridesInDirection` (`Blizzard_GamepadSmartNavigation/Utility.lua:414-486`), guarded when absent. The trace line is "nav set".

- Up and down walk the list in order, headings included: left to itself the d-pad goes to the nearest button on screen, and a row scrolled out of view is farther than the details below, so down would leave the list (jump overrides do not scroll to an out-of-view row). Down from the last row stays in the list.
- Right from a row enters the details at the made item. Down and up there walk the made item, the reagents and Map Pin in order, because a reagent out of view is farther than something on screen. Right from any control in the details stays on it, since left to itself it would reach up and right into the list. In the open place list, down from its button enters the first entry and up and down walk the entries.
- Back target: left from any control in the details, and up from the made item, lead to the list row or heading the cursor last highlighted (`ns.NoteListFocus`), else the first row. A recipe row's right and the back target are set again whenever the selection, the rows or the details change.
- Focus scroll: a row, a heading or a reagent the d-pad reaches is scrolled into view on its `OnEnter` (`ns.ScrollRowIntoView`), because jump overrides do not scroll. When the details open and shorten the list, the selected row is brought into view once the frames have their new size.
- Combat: overrides are cleared on `PLAYER_REGEN_DISABLED`, which comes just before the lockdown while they still can be, and set again on `PLAYER_REGEN_ENABLED`. A change during combat waits for its end. A row's right override left from before combat would show the blocked-action message instead of moving. They are also cleared when the list rebuilds (rows are reused for other recipes; the build's end sets them again) and when the panel hides, and set again when it shows.

## Trainers

- Trainers list recipes up to their own rank.
- The trainer window is `Blizzard_TrainerUI` (`Mainline/Blizzard_TrainerUI.lua` with `Blizzard_TrainerUI_Camelot.lua` overrides; Gethe/wow-ui-source, `forever` branch). It listens to `TRAINER_UPDATE` and rebuilds its whole list in `ClassTrainerFrame_Update` on each one, and `SetTrainerServiceTypeFilter` fires it. The old scan turned the available, unavailable and used filters on, held them over several frames and set them back, so the player saw the list change and change back (owner, Deck, 2026-11-27: "the engineering trainer flickers"). The cause is from reading the source and the scan's code, not yet measured on the Deck.
- The main scan never sets a filter. It reads the services the window shows under the player's own filters (`GetNumTrainerServices` counts only those), in steps of 3 ms a frame (a service tooltip is about 1.5 ms, so a step stays under the kit's 5 ms frame bar), and takes each service's spell ID from `C_TooltipInfo.GetTrainerService(index)` (a `Spell` tooltip's `id`). Services of a type the player's filter hides are not read, and their number cannot be known without changing the filter, so the trace names the hidden types ("trainer filters off=used").
- The spell cache: the ID is saved per account by trainer NPC and service name (`RecipeVacuumDB.trainerSpells[npcID][name]`, docs/data.md, "Trainer spells"), so a trainer's tooltips are read once, on any character, ever. The name is only a key into what the tooltip said; the recipe is matched by the spell's ID (`GetTradeSkillLineForRecipe`, or any service of a profession trainer), never by the recipe's name. A client in another language reads its own names once more and finds the same IDs.
- The learned read (owner, 2026-11-27, cairn:mq5g8: "Tooltip ids seem better, can we throttle our query?"). Learned ("used") services are listed only while the "used" filter is on, and the tooltip needs the service's index, so the read must set the filter. It is a series of atomic one-frame passes, each starting and ending with "used" hidden, so the window never holds the change across a frame (the flicker came from holding filters across frames; owner, Deck, 2026-11-27: "the engineering trainer flickers"). One pass, in one frame: `SetTrainerServiceTypeFilter("used", true)` (booleans, as Forever's own `TrainerUI` code passes them); walk the rows by name; for the next "used" services not in the spell cache, read the spell ID from the tooltip; `SetTrainerServiceTypeFilter("used", false)` inside a `pcall` and the filter read back; then the passes' saving. The next pass runs the next frame. It runs at a profession trainer (`IsTradeskillTrainer()`, or one where the scan saved a recipe), out of combat, still at that trainer, and only when the player hides "used". It starts in the frame after the visible scan's finish frame, and at most once a visit (each `TRAINER_SHOW` is a visit), so a rescan in the same visit (a purchase, a filter change) does not toggle the filter again. A window that shows 0 services starts no read: the read waits for a finished scan (owner, 2026-11-27). Measured on the Deck before this (2026-11-27, npc 1241, a Blacksmithing trainer for a character without Blacksmithing): 3 passes over 2 visits, 26 to 32 ms each, 13 to 17 ms per filter toggle, 0 learned rows each time, which was correct; the second pass of the first visit came from the scan's end re-queuing it.
- Done is kept for the account (`RecipeVacuumDB.learnedReads`, docs/data.md, "Learned reads"; owner, 2026-11-27: "Does per character matter? I'd argue not, I won't see something different than you or another at a trainer"). A read is done when a pass completes with nothing left: 0 learned rows is an answer, not a gap. A trainer is read again only when the visiting character knows a recipe of that trainer's profession with no trainer source recorded since the trainer's last read on that character (`ns.NoteUnsourced`, fed by the profession window's read of known recipes), which covers recipes learned before install or with the addon off. No profession gate: the read also runs at trainers of professions the character lacks, for the data and for a player looking before switching (owner, 2026-11-27: "I don't think the gate is useful, it's only once anyway and is good for data gathering and if I want to switch professions by looking first"). Traces: "not read: done, and this character knows no recipe of skill line L without a trainer source since", "read again: this character knows N more recipes ...", "not read again this visit". The working build has a Learned Services [Read] button that forces one read at the open trainer.
- The throttle: the first pass reads one service (`LEARNED_START_BATCH`). Each pass is timed whole (filter on, walk, tooltips, filter off, saving) and the next batch is sized so a pass stays under `LEARNED_PASS_MS` (4 ms, under the 5 ms bar), at most doubling a step. Every pass reads at least one service whatever its cost, so a slow machine finishes later and never starves; there is no "try again next time" on a time cap. Services already in the cache cost no tooltip and are saved in the same pass, within the time. Progress is kept by service name in the job and in the saved cache, so the next pass, a closed window and the next visit all continue where it stopped. Cost and skill on a "used" row are hidden by Blizzard, so they are saved only when above 0 and a saved value is kept otherwise (`Save` skips a missing field); the main scan does the same for a "used" row.
- The named atomic exception to the 5 ms bar: one pass whose only work is one service (one tooltip) plus the two filter calls. If that alone is over 5 ms the trace says "ATOMIC EXCEPTION" with the numbers, and the finish line counts them. The filter calls cannot be split across frames without showing the change. Nothing else here is exempt.
- Our own filter calls fire `TRAINER_UPDATE`, which is not the player's: they are counted, not acted on, for the length of the read and 0.5 s after it (the counts inside the two calls, so dispatched synchronously, and between passes, so deferred, are separate). The player's own change shows instead as a different service count at the start of a pass, which is counted as a change of the list (the next pass walks the new list by names, so nothing restarts); five changes (`TRAINER_MAX_RESTARTS`) end the read, keeping what it saved. The read also ends, keeping its progress, on combat, the window closing, another trainer opening, the player showing "used", an error (the restore is in a `pcall` and a filter found still on ends the job and is traced as a mismatch), and the pass cap (`LEARNED_MAX_PASSES`, 300). A read left unfinished is asked again on a later visit (at most `MAX_ITEM_ATTEMPTS` reads a session) only when a "used" row had no name yet or a service gave no spell.
- Trace per pass: "TRAINER learned pass N of npc X: rows, services to read, spells from tooltips and from the cache, left; filter on, tooltips, filter off, whole filter window and pass ms (batch, next); TRAINER_UPDATE inside the calls and since the last pass; filter used back; before: and after: selection (`GetTrainerSelectionIndex`, the window's `selectedService`, `isFocused`, the focused button's `displayIndex`)". A finish line per trainer: passes, services seen, tooltips read and their ms, cache hits, saved, new, skipped, total and worst pass ms, atomic exceptions, list changes, `TRAINER_UPDATE` counts, attempt and state. "trainer updates npc=…" gives the total when the window closes, and "after the window settled" the selection once more. Working-build timing: `trainer learned pass`.
- Known gaps of the learned read, none measured on the Deck yet: with categories on, `ClassTrainerFrame_Update` restores the gamepad focus by data index (`UpdateGamepadFocus`, `GetGamepadSelection`), so after a filter change the cursor can land one row off, and a collapsed category that the selection falls in is expanded by that update (`SetCollapsed(false)`); the per-pass selection trace is there to show it. Each pass makes two rebuilds of the window's list, so a long read is many; the batch sizing makes the passes few. A taint path exists only if `TRAINER_UPDATE` is dispatched synchronously inside our calls and the player enters combat with the window open (combat is checked at the start of each pass, not between the two calls). A player's change that leaves the service count the same is not seen as a change, which costs nothing because every pass walks the list by name. The cache key is the service's name, so two services of one trainer with one name are taken to teach one spell, and a trainer that changes a service's spell under the same name keeps the old ID until the cache is cleared (unseen so far). The service cache grows with the trainers visited (a spell ID and name per service).
- `TRAINER_UPDATE` (a filter change by the player, a purchase), or a service name that arrives after the scan skipped that service (`TRAINER_SERVICE_INFO_NAME_UPDATE`), during a scan makes it read again from the top, at most 5 times; services already asked for cost no tooltip. One after a scan ends starts a scan again. A scan cut short (the window closed, another trainer opened, the restart cap) still reports what it saved. No creature GUID at the show (the client hides it) asks again on the next update.
- Trace "TRAINER scan of N services read in S steps, X ms (T ms of tooltips, worst step W ms), closed in C ms and finished in F ms; R recipes, K new; skipped: reason n, ...; filters off: ...; restarts n". Skip reasons: header, rank step, no category, no spell, not a profession, no name yet. Working-build timings: "trainer scan step", "rank", "visit", "finish", "tooltips".
- The scan's closing work is one step a frame ("trainer scan rank", "visit", "finish"): with the old filter restore it took 12.6 ms in one frame on the Deck (2026-11-26).
- `IsTradeskillTrainer()` is false for some NPCs that teach recipes (Westfall's Odd Child, six Alchemy recipes).
- `C_TradeSkillUI.GetTradeSkillLineForRecipe(spellID)` returns a profession line for recipes and for rank spells, and nothing for class spells. `C_TradeSkillUI.GetRecipeInfo` is non-nil for rank spells too.
- `GetTrainerServiceInfo` returns a category as its sixth value. Recipes have one ("Elixirs", "Camping"); ranks ("Journeyman Herbalism") have none. Blizzard's trainer window groups by the same value. `GetTrainerServiceStepIndex` marks only the next rank.
- The service list can arrive a moment after `TRAINER_SHOW`, and the window's filter hides known recipes.

- The dungeon journal does not load on Forever: `C_EncounterJournal and EJ_GetNumTiers` is nil (owner, build 71091, 2026-11-25), so boss loot cannot be read from the client.

## Rank books

A rank book (Expert Fishing - The Bass and You, item 16083) is a recipe item whose item spell is the rank it teaches (`C_Item.GetItemSpell`: 19889, Expert Fishing; not the trainer-style rank spell, and `IsPlayerSpell` is the same check as `C_SpellBook.IsSpellKnown`, Blizzard_DeprecatedSpellBook/Deprecated_SpellBook.lua); its recipe subclass names the profession, and "Requires Fishing (125)" and "Already known" come as tooltip data (build 71091, 2026-11-25). The books are sold by a few vendors spread across the world, not by trainers (owner, 2026-11-25), so they are recorded as vendor sources like any recipe item. Primary profession ranks come from trainers instead: a trainer lists them as services with a spell and no category (Apprentice Alchemist 2259, Journeyman Alchemist 3101, Expert Alchemist 3464; build 71091, 2026-11-25), each shown once the one before it is learned. The addon keeps the step (docs/data.md, "Ranks"). Trainers have tiers, and a trainer lists ranks only up to the next one the character can learn: in Darnassus with Journeyman Alchemy, Milla Fairancora listed Apprentice only, Sylvanna Forestmoon up to Journeyman, Ainethil up to Expert (build 71091, 2026-11-25). So a trainer's top rank is learned only by visiting with the rank below it; Forever guides list Ainethil as an Artisan trainer (WoW-Professions, "WoW Forever Alchemy Trainer Locations"). Forever guides (Wowhead Forever profession overviews, Warcraft Tavern Forever trainer list; not yet checked in game) agree on the Expert book vendors above and add two more paths: Artisan Cooking, First Aid and Fishing come from quests (Triage for First Aid), and Forever adds manuals that teach a gathering profession without a trainer (Wowhead's Forever profession guides; Overgear, "WoW Forever professions changes").
